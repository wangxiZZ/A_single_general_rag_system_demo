### P0（影响验收口径或题目硬要求）

#### G-01 关键词通道把整词合并成伪复合词，自然语言查询 0 命中（✅ 已修复，M8-01）
- **现象**：同一库 `mode=keyword` 查「年假」返回 1 条，查「年假有几天」返回 **0 条**；
  `vector`/`hybrid` 正常。
- **证据**：`infra/postgres/lexical.py:60-85` 的 `tokenize()` 把连续单字合并，
  「年假有几天」被 jieba 切成单字后合并为 `年假有` + `几天`；`to_tsquery` 里没有 `年假`。
  线上实测见 `测试方案.md` R-01。
- **影响**：题目要求"三种召回可实际调用"，关键词通道对**自然语言问句**实际不可用
  （只有短术语/编号类查询有效），benchmark 的 keyword Recall 1.0 是短问法下的结果。
- **改法**（任选，建议 1+2）：
  1. 停用词表补高频虚词（`有/是/的/多少/几/怎么/如何/哪些/什么/是否/多久`…），
     减少"把虚词粘进复合词"；
  2. 连续单字 run 除合并整串外，**同时产出 2-gram 与单字**（索引侧与查询侧用同一规则，
     查询仍是 OR 拼接，召回优先、排序由 `ts_rank_cd` 兜底）；
  3. 加单测：`tokenize("年假有几天")` 必须包含 `年假`；集成用例见 `测试方案.md` R-01。

#### G-02 缺 `GET /documents/{doc_id}/images/{img_id}`（原图接口）（✅ 已修复，M8-02）
- **现象**：实测 404；`SearchHit.image_url` 恒为 `null`。
- **证据**：`api/routers/documents.py`（全文 80 行）无该路由；`grep image_url src` 只有
  `domain/models.py:185` 与 `api/schemas.py:59` 两处声明、无赋值。
- **影响**：题目 §5 要求"保留图片与原文档、所在位置的对应关系"——数据在
  `doc_image(page_no,bbox,seq)` 与 `chunk.image_id` 里，但**对外没有任何入口能看到原图**，
  演示与验收只能用 `/chunks` 的 `image_id` 字符串证明。`实施计划.md:310` 明确承诺该接口
  及 `X-Page-No`/`X-Bbox`/`X-Seq` 响应头。
- **改法**（约 15 行，能力已齐备：`repo.list_images`、`Storage.read`）：
  `documents.py` 增路由 → 按 `(kb_id, doc_id, image_id)` 取 `DocImage` → 校验
  `file_path` 属于该文档 → `await storage.read(file_path)` → `Response(content=..., media_type=...)`
  并带三个定位响应头；未找到返回 404。同时在 `search_service._hydrate` 与
  `graph_search` 里对 `chunk.kind is IMAGE` 填 `image_url`（G-04）。

#### G-03 缺 `GET /kbs/{id}/graph`（实体子图）
- **现象**：实测 404。
- **证据**：`api/routers/kbs.py`（61 行）无该路由；`domain/ports.py` 的 `GraphStore` 也没有
  "列子图"能力（只有 `candidate_entities`/`expand`）。
- **影响**：`实施计划.md:313` 承诺的演示接口不存在。题目说明"仅展示关系图不算完成"，
  所以它**不是硬要求**；但文档对账会算缺口，且演示时无法直观展示图谱。
- **改法**：`GraphStore` 增 `async subgraph(kb_id, limit) -> tuple[list[Entity], list[Relation]]`，
  Cypher 全带 `{kb_id: $kb}`（`MATCH (e:Entity {kb_id:$kb}) ... LIMIT`），路由只组装 JSON；
  或者从文档里删掉这条接口并标注"图谱可视化不在本期范围"（二选一，不能两处不一致）。

#### G-04 图片块命中时 `image_url` 恒空（✅ 已修复，M8-02）
- **证据**：`application/search_service.py:220-233`、`application/graph_search.py:54-70`
  构造 `SearchHit` 时没有填 `image_url`。
- **改法**：`_hydrate`/`graph_search` 取 `chunk.image_id`，拼 `/api/kbs/{kb}/documents/{doc}/images/{img}`；
  依赖 G-02 的路由存在。

#### G-05 失败路径可能留下 chunk / doc_image 行（"失败无残留"被破坏）（✅ 已修复，M8-03）
- **现象**：若在 `persist` 之后、`update_document(CHUNKED)` 处抛**非** `NotFoundError`
  异常（PG 抖动、连接池超时等），worker 只把文档标 `failed`，`chunk`/`doc_image`/
  `chunk_count` 都留着；`/chunks` 仍能读到失败文档的内容。
- **证据**：`application/ingest_pipeline.py:153-159` 只捕 `NotFoundError`；
  `worker/loop.py:111-126` 的 `_mark_failed` 只改状态与 error；清理逻辑在
  `application/indexing.py:132-157`，**不覆盖 pipeline 阶段**。
- **影响**：题目点名的"处理失败"边界口径是"无脏索引、可重试"，这里在罕见路径上不成立；
  重试又会基于旧块重建（`unique(doc_id,seq)` 可能冲突）。
- **改法**：把 `indexing.py:132-157` 抽成 `IndexingService.cleanup_failed(kb_id, doc_id)`，
  `IngestPipeline.process` 的 `except` 与 `worker._mark_failed` 共用；清理时同时删
  `data/images/<doc_id>/`。

#### G-06 同步 `Parser.parse` / `chunk_document` 在协程内阻塞事件循环（✅ 已修复，M8-04）
- **证据**：`application/ingest_pipeline.py:87`（`self._parser.parse(...)`）与 `:93`
  （`chunk_document(...)`）是同步调用，没有 `anyio.to_thread.run_sync`。
  `domain/ports.py` 与 `architecture.md:52-54` 明确"`Parser.parse()` 是同步 CPU 方法，
  由 worker 放进线程池"；`AGENTS.md` §3.11 是硬约束。
- **影响**：解析大 PDF（数十秒）期间，`/healthz`、其他 HTTP 请求、worker 心跳全部排队；
  演示时表现为"上传大文件后页面卡住/健康检查超时"。
- **改法**：`await anyio.to_thread.run_sync(lambda: self._parser.parse(data, filename=..., mime=...))`，
  分块同理（或整段丢进同一个线程任务）。注意 `chunk_document` 是纯 CPU，可放在 parse 之后同一线程里。

### P1（文档承诺未实现 / 一致性缺陷）

#### G-07 混合检索降级时没有 `channels[] = graph:error` 标记
- **证据**：`application/search_service.py:136-155` 用
  `gather(..., return_exceptions=True)` 收集错误后**直接丢弃**，只有全部通道都失败才抛。
- **影响**：`实施计划.md:325` 承诺"`hybrid` 降级并在 `channels[]` 标 `graph=error`"；
  调用方无法区分"图没命中"与"图挂了"（Skill 侧的重试决策因此失真）。
- **改法**：`_collect_channels` 返回 `(rankings, channel_errors)`，把 errors 写进
  `SearchHit.debug["channel_errors"]`，并在无命中时也回传状态。

#### G-08 `meta.low_weight` 只写不读，融合时不降权
- **证据**：`application/image_chunks.py:160` 写入 `low_weight`；`fusion.py`、
  `search_service.py` 无任何读取；只有 `web/templates/chunks.html:35` 显示徽标。
- **影响**：`实施计划.md:227`、`design.md:45` 承诺"检索融合时对低权重块降权，而不是排除"，
  VLM 失败的占位图描述与正文同权竞争。
- **改法**：`_hydrate` 把 `chunk.meta.low_weight` 放进 `hit.debug`，`fusion` 计算分数时对
  该 hit 乘系数（如 0.5）；权重写进配置（`IMAGE_LOW_WEIGHT_FACTOR`）并同步三处配置。

#### G-09 重排实现与文档不一致，`RERANK_*` 是空转配置
- **证据**：`grep -rn "rerank_enabled|rerank_base_url|rerank_model|rerank_api_key"` 只命中
  `config.py:105-110`；`main.py:154` 注入的是 `LLMListwiseReranker(llm)`（用 LLM Key，
  不用 `RERANK_API_KEY`）；`SearchRequest.rerank` 是 `bool`，没有 `rerank=llm|on` 枚举。
- **影响**：`实施计划.md:274-276`（`on`→cross-encoder `bge-reranker-v2-m3`、
  `llm`→listwise）、`README.md:187`（"开启需同时配置 `RERANK_*`"）、`design.md:100`
  三处口径不一；用户按 README 配 `RERANK_*` 完全不生效。
- **改法**（二选一，推荐 A）：
  - **A**：实现 `infra/llm/rerank.py` 的 cross-encoder 客户端（读 `RERANK_*`），
    `SearchRequest.rerank: Literal["off","on","llm"]`，`on`→cross-encoder、`llm`→listwise；
  - **B**：不改代码，改文档——把 `rerank` 定性为"bool，等价于 LLM listwise"，
    并从 `config/.env.example/compose` 三处删除未使用的 `RERANK_*`（需同步删字段）。
    两种做法都必须让 README/config 注释与实现一致。

#### G-10 `retry` 不清三路残留、`attempts` 不累计（✅ 已修复，M8-05）
- **证据**：`application/document_service.py:141-152` 只 `delete_chunks`；
  `enqueue_ingest_job` 新建 job，`attempts` 从 0 开始（`repository.py:475-515`）。
- **影响**：`实施计划.md:307` 要求"先清理残留"且 `attempts+1`；残留索引会让重试后的
  文档在索引阶段之前就能被检索到（脏命中）。
- **改法**：`retry_document` 里按 `delete_document` 的顺序清 vector/lexical/graph（各自
  `try` 不静默）+ 清 `doc_image` + 删图片目录；`attempts` 由旧 job 的最大值 +1 传入新 job。

#### G-11 `reindex` 失败被静默吞掉
- **证据**：`application/reindex.py:32-35` `except Exception: logger.exception`；
  `api/routers/kbs.py:56-61` 状态只有 `running/done`，无 `failed`/`error`；
  `app.state.reindex_tasks` 只增不删（`main.py:287`）。
- **影响**：`chunker_version` 不匹配（`indexing.py:77-81`）这类"应显式报错"的情况变成
  静默跳过；CLI `rag-kb reindex` 会把失败读成成功。
- **改法**：`ReindexService.reindex_kb` 返回 `(succeeded, failed[])`；任务记录
  `{kb_id, status: running|done|failed, error}`；状态接口返回 failed 明细；完成后清理/加 TTL。

#### G-12 父块 token 可能超过 `PARENT_MAX_TOKENS`
- **证据**：`application/chunking.py:207-212` 按段累加 token 决定分组，
  `:276-288` 用 `"\n".join(...)` 生成内容并重新估算 token——换行符未计入分组预算。
  构造 60 个 ×30 字段落可得到 `token_count=1226 > 1200`。
- **影响**：破坏 `qa_service.py:57-61` 的"单条父块天然不超预算"前提，`QA_MAX_CONTEXT_TOKENS`
  校验失去意义。
- **改法**：分组时把分隔符长度计入，或先 join 再判上限；加单测断言
  `max(parent.token_count) <= parent_max_tokens`。

#### G-13 跨页 PDF 块的 `bbox` 为 `None`
- **证据**：`application/chunking.py:102-108` 仅当所有段落同页才输出 bbox。
- **影响**：`AGENTS.md` §3.4 与 `design.md:60` 要求 PDF 块"必须带 `page_no + bbox`"；
  跨页块只能给页码、无法给坐标，��用高亮/定位会缺失。
- **改法**：按页边界拆块（推荐，语义最清楚），或按页分别记录 bbox（可放 `meta.bboxes[]`），

#### G-14 只有标题没有正文的节整节丢失
- **证据**：`application/chunking.py:138-141` 的 `flush()` 只在 `current` 非空时产生 section。

#### G-18 图谱打分未归一化，且打分逻辑在 infra

#### G-19 调试/可观测字段与契约不一致

## 6. 已核实无问题（可放心答辩的部分）

- **分层与依赖方向**：`domain` 只依赖标准库；`api`/`web`/`worker` 不 import `infra`；
  `mcp_server` 不 import `rag_kb`（AST 扫描）；`config.py` 是唯一 env 读取点。
- **数据库 schema**：七张表逐列与文档一致；`chunk_lex.tsv` 是 `GENERATED ... STORED` + GIN；
  `unique(doc_id, seq)`；`parent_id` 外键 `DEFERRABLE`；除 `chunk.image_id` 为 `SET NULL`
  （语义合理）外全部 `ON DELETE CASCADE`。
- **kb_id 隔离**：PG 检索类 SQL、Neo4j 全部 `MATCH/MERGE`、Milvus filter 均带 `kb_id`；
  三个隔离用例做的是"先正例后负例 + 计数"强断言。
- **Milvus 配置**：`partition_key=kb_id`、HNSW(M=16, efConstruction=200)、`ef=64`、
  `consistency_level="Strong"`、维度不一致 `ConfigurationError`、非 child 拒写。
- **图谱闭环**：边带 `chunk_id/evidence_span/kb_id/doc_id`；`delete_by_doc` 边→Chunk/Doc→
  孤儿 Entity；`expand` BFS 有跳数/邻居上限且每节点带 `kb_id`。
- **错误码**：413（不建行不落盘）、415（扩展名+magic bytes）、409（带
  `existing_document_id`）、422、404、503（`mode=graph` 且图存储缺失）均已落地且有用例。
- **配置同步**：54 个 `Settings` 字段在 compose `environment` 与 `.env.example` 100% 同步。
- **解析器**：PDF 页内 y→x、bbox、char 偏移、图片过滤（<120×120px/<8KB）、无文本抛
  `NoExtractableTextError`；docx 按 XML 顺序、`page_no/bbox=NULL`、标题样式/outline、
  表格线性化、页眉页脚排除。
- **模型客户端**：429/5xx/timeout 指数退避、4xx 不重试、信号量限流、embedding 批量顺序
  保持与维度校验、`structured_json` 去 code fence。
- **摄取状态机与 tombstone**：三次存在性检查、`IngestAbortedError` 不标 failed、补清图片文件。
- **评测**：`benchmark.md` 的 `mode × rerank` 指标、`graph-eval.md` 的 P/R/F1 与
  `evidence_span` 有效率 1.0，均有脚本与单测支撑。
