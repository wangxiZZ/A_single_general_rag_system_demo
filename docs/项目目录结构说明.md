2. 哪些依赖方向是被禁止的（§3）

## 3. 分层与依赖方向（硬约束）

```
        api/  web/  worker/              入口层：协议适配、请求校验、页面渲染
                 │
                 ▼
            application/                 用例编排，事务边界在这层
                 │        ▲
                 ▼        │ 实现
             domain/ ◄────┴──────────  infra/     适配器：PG / Milvus / Neo4j / 解析器 / LLM
        （模型与端口协议）                （在 main.py 启动期注入）
```

| 规则 | 说明 | 反例 |
|---|---|---|
| `domain` 不依赖任何人 | 只放 dataclass / Protocol / 枚举 / 领域异常 | `domain/models.py` 里 `import psycopg` |
| `application` 只依赖 `domain` | 通过端口调用外部能力，可被 API、worker、CLI 复用 | `application/search_service.py` 里 `import fastapi` |
| `infra` 实现 `domain` 的端口 | 允许 import 第三方库，但不 import `api`/`web` | `infra` 里反向 import `application` |
| `api` / `web` / `worker` 薄 | 只做参数校验、调用用例、组装响应 | 路由函数里写 SQL 或分块逻辑 |
| `mcp_server` 只能走 HTTP | 不导入 `rag_kb`，避免出现第二套检索实现；Skill 安装目标是 `.claude/skills/rag-kb/` | MCP 里 `from rag_kb.infra.milvus import ...` |
| 端口方法统一异步 | I/O 端口一律 `async def`；同步 SDK 由适配器用 `anyio.to_thread` 包装；`Parser.parse()` 同步 | 在协程里直接调用 psycopg / pymilvus / neo4j 同步客户端 |
| 算法留在 application | 分块、RRF、实体链接与打分属于业务逻辑 | 把种子链接或路径打分写进 `infra/neo4j/store.py` |

> 端口清单（M1-02）：`MetadataRepository / VectorStore / LexicalIndex / GraphStore / Embedder /
> LLM / VLM / Reranker / Parser / Storage`。
>
> 自检：`uv run pytest tests/unit/test_layering.py`（M1 落地，用 AST 解析 import 图断言上述规则）；
> `uv run pytest tests/unit/test_config_compose_sync.py`（M1 落地，校验 Settings 与 compose 字段一一对应）。
>
> 引擎侧的隔离另有约束：所有检索必须带 `kb_id`。Milvus 用 `partition_key=kb_id` **加上**强制等值
> 过滤（分区键只负责路由，不带过滤仍会扫全部分区）；PG 用 `where kb_id = %s`；Neo4j 用
> `{kb_id: $kb_id}`。

## 6. 新增文件放哪：四步判定

拿到一段新代码时依次问：

1. **它依赖第三方库或具体存储吗？** 是 → `infra/`；否 → 下一步。
2. **它只定义"要什么能力"而不实现吗？** 是 → `domain/ports.py`；否 → 下一步。
3. **它编排多个步骤或管理事务吗？** 是 → `application/`；否 → 下一步。
4. **它是协议适配（HTTP 参数、页面、MCP）吗？** 是 → `api/` / `web/` / `mcp_server/`；否则大概率属于 `domain/models.py`。

补充规则：

- 纯函数且值得单测的算法（分块、RRF、实体链接与打分、引用校验）放 `application/`，不要塞进 `infra/`——否则测试必须起容器。
- 一段 SQL 只能在 `infra/postgres/sql/` 里出现；Cypher 只能在 `infra/neo4j/`。
- 配置项只能加在 `config.py`，并同步 `.env.example` 与 `docker-compose.yml`；随后跑 `tests/unit/test_config_compose_sync.py`，三处不一致即失败。
- 新增 I/O 端口时默认 `async def`；同步 SDK 必须在适配器内部用 `anyio.to_thread` 包装。
- 新增文档：同一 commit 更新本文 §2 的文档列表；新增顶层目录或分层包时更新 §4/§5。

## 7. 命名约定

| 对象 | 约定 | 示例 |
|---|---|---|
| 模块 | 小写下划线，名词或动名词 | `ingest_pipeline.py`、`chunking.py` |
| 端口（Protocol） | 能力名，不带 `I` 前缀 | `VectorStore`、`Embedder` |
| 适配器实现 | `<能力><存储>` | `MilvusVectorStore`、`PgLexicalIndex` |
| 用例服务 | `<领域>_service` | `qa_service.py` |
| 数据模型 | 单数名词，`frozen=True` 优先 | `Chunk`、`SearchHit` |
| 表名 | 单数小写 | `kb`、`document`、`chunk`、`ingest_job` |
| Milvus 字段 | 小写下划线，主键固定 `id` | `kb_id`、`doc_id`、`vector` |
| 测试文件 | `test_<被测模块>.py` | `test_chunking.py` |
| 环境变量 | 大写下划线，与 Settings 字段同名 | `CHUNK_TARGET_TOKENS` |

## 8. 空目录与占位文件

git 不追踪空目录，因此以下位置放了 `.gitkeep`，克隆后才不会消失：

```
data/.gitkeep
scripts/bench/.gitkeep
```

`scripts/migrate.py`、`src/rag_kb/web/` 下的模板/静态文件与 `skills/rag-kb/SKILL.md` 已落地，
不再保留对应 `.gitkeep`。`.claude/skills/rag-kb/SKILL.md` 是安装副本，与源文件同步提交。

各分层包的 `__init__.py` 目前是空文件（保持包可导入）；`mcp_server/__init__.py` 同样为空。
注意 `domain/` 的 `__init__.py` **不得**做任何 re-export 便捷导入——那会诱导
`from rag_kb.domain import PgChunkRepo` 这类跨层引用，破坏 §3 的约束。

真实文件落地后（如 `cli.py`、`worker/loop.py`、`skills/rag-kb/SKILL.md`），同一 commit 内
删除对应位置的 `.gitkeep` 并更新本节的占位清单；不要让"占位文件"和"已实现文件"同时存在。

## 9. 变更规则

1. 新增顶层目录或新增一个分层包：同一 commit 内更新本文 §2 与 §4/§5。
2. 目录职责变化（例如把图抽取从 `application` 挪到 `infra`）：更新 §3 的表格，并在 `docs/技术选型文档.md` 加一条 ADR 说明原因。
3. 本文与代码不一致时，**以代码为准并立即修文档**；不要留下"文档描述另一个系统"的状态。
4. 新增 `docs/` 下的文档：同一 commit 内把它加入 §2 的文档列表。
5. 文档修订期间：以 `docs/文档修订任务清单.md` 的顺序与决策为准；接口/字段变更必须在同一
   commit 内同步 `docs/技术选型文档.md` 的 ADR 与本文对应章节。
