# 待实现方案（加分项）

> 以下方案均标注 **待实现**：本文只写问题、收益、代价与验证方式，不包含已落地代码。
> 排序按「对当前演示的收益 / 成本」从高到低。验证默认复用
> `scripts/bench/run_bench.py` 与 `tests/fixtures/bench/qa.jsonl`，保证可横向比较。

## 1. 版面感知解析 + OCR

**问题**：当前 PDF 解析按 `(y0, x0)` 阅读顺序、单栏优先；扫描件直接失败；复杂表格/公式
只能按文本行拼接。真实企业文档里这三类占比不低。

**收益**：

- 扫描件可入库，扩大可用素材范围；
- 多栏、页眉页脚、表格结构还原后，chunk 边界与检索命中率都会提升；
- 表格可按行/列成块，回答"某列的取值"这类问题更可靠。

**代价**：

- 需要 OCR/版面模型（如 PaddleOCR、布局分析模型），本地 CPU 推理慢，GPU 增加部署门槛；
- 解析耗时上升 2–10 倍，worker 需要更明确的超时与分页处理；
- 表格结构进入 chunk 后，`char_start/char_end` 的坐标系要重新定义（当前是串联文本偏移）。

**验证方式**：

1. 新增 3–5 份扫描件/双栏/表格 PDF 作为夹具；
2. 断言解析出文本与表格行，且 `page_no/bbox` 正确；
3. 用现有 25 条金标跑 `run_bench.py`，对比 Recall@5 与 MRR 不下降；
4. 为扫描件新增图片/表格类问题，检查引用可回溯。

## 2. 查询改写与混合重排

**问题**：用户提问常与文档措辞不同（"年假" vs "带薪年休假"），单轮查询 + 单路召回会漏；
当前重排是可选 LLM listwise，默认关闭，且只对已召回的 30 条候选重排。

**收益**：

- 同义词/口语化问题召回更稳；
- 多查询（multi-query）可提升长尾问题的 Recall@10；
- cross-encoder 精排通常比 LLM listwise 更便宜、更稳定。

**代价**：

- 查询改写引入一次 LLM 调用（或同义词表），检索路径不再零 LLM；
- 多查询会把向量检索放大 2–3 倍，延迟与 embedding 成本上升；
- 需要缓存与超时控制，否则首字延迟不可接受。

**验证方式**：

1. 记录改写前后的查询与命中，人工抽检 20 条；
2. 在 `mode=hybrid` 上对比 `rewrite on/off × rerank on/off` 的 Recall@5/10、MRR、nDCG@10；
3. 监控 P95 延迟与单次问答的 token 成本，设定可接受上限；
4. 对不可回答题检查误召回是否增加。

## 3. 增量索引与文档版本化

**问题**：文档更新目前要重新上传（同 sha 去重会拦截），`reindex` 也是整篇重建；
大文档的 embedding 与图谱抽取成本高。

**收益**：

- 只对变化的 chunk 重新 embedding/抽取，索引时间与成本按改动比例下降；
- 保留版本后，回答可以注明"依据 v3 文档"，便于审计；
- 删除/回滚更精确，不会误伤未变化的实体与边。

**代价**：

- 需要文档版本表与 chunk 级 diff（标题路径、内容哈希）；
- 三路存储都要支持按 `(doc_id, version)` 更新，Milvus 主键与 Neo4j 边要带版本；
- 与现有 `chunker_version`/确定性 chunk id 的兼容需要迁移方案。

**验证方式**：

1. 构造"只改一段"的文档，断言只有该段的 chunk id 变化；
2. 对比全量重建与增量更新的耗时、embedding 调用次数；
3. 更新后三路检索结果与全量重建一致（同查询同 top-k）；
4. 回滚旧版本后，原文引用与索引计数一致。

## 4. 多租户与鉴权

**问题**：当前无鉴权，定位本机/内网；`kb_id` 是唯一隔离维度，没有用户/租户概念。

**收益**：

- 可对外部署，按用户或租户隔离知识库；
- 审计（谁上传、谁查询）与配额控制成为可能。

**代价**：

- 所有表、Milvus 分区/过滤、Neo4j 键都要加 `tenant_id`；
- 需要认证中间件、Token 管理、权限模型（读/写/管理）；
- MCP/Skill 需要携带凭证，配置与演示复杂度上升。

**验证方式**：

1. 跨租户检索断言 0 命中（复用现有隔离测试结构）；
2. 未认证请求返回 401，越权返回 403；
3. 删除/重建只影响本租户计数；
4. 审计日志可按租户过滤。

## 5. 在线评测与反馈闭环

**问题**：当前 `query_log` 只记录延迟与命中，无法判断"这次回答好不好"；金标更新靠手工。

**收益**：

- 上线后可持续观察零命中率、引用拒答率、用户点踩；
- 反馈样本可回流成新的评测集，驱动参数调整；
- 能定位问题出在召回、融合还是生成。

**代价**：

- 需要前端反馈入口与标注流程；
- 用户数据涉及隐私与留存策略；
- 离线指标与线上反馈口径不一致时容易误判。

**验证方式**：

1. 在 `query_log` 上增加 `feedback` 关联表，统计点踩率；
2. 抽样 50 条线上问题人工标注，比较离线/线上指标相关性；
3. 用反馈样本扩充 `qa.jsonl` 后重跑 benchmark，观察指标变化是否合理；
4. 保证反馈数据脱敏、可删除。

## 6. 流式回答与引用先行

**问题**：`/ask` 等待完整生成后一次性返回，长回答首字延迟高；引用在回答结束后才可见。

**收益**：

- 首字延迟显著下降，交互更接近对话产品；
- 可先返回检索到的引用，再流式补答案，用户能更早判断可信度。

**代价**：

- FastAPI 需要 SSE/WebSocket 与取消传播；
- 引用回校验发生在生成后，流式场景要定义"边生成边校验"或生成后修正；
- Web 页面与 MCP 客户端都要处理增量协议。

**验证方式**：

1. 对比首字节时间与总耗时；
2. 断言流式结束后最终文本/引用与非流式一致；
3. 客户端断开时 LLM 调用被取消，无孤儿任务；
4. 引用校验失败的降级路径有测试。

## 优先级建议

| 方案 | 收益 | 成本 | 建议 |
|---|---|---|---|
| 查询改写 + 混合重排 | 中 | 低–中 | 先用 benchmark 验证收益，再决定是否打开默认重排 |
| 增量索引 | 中 | 中 | 文档量大后再做 |
| 版面感知 + OCR | 高 | 高 | 有扫描件需求时优先，需 GPU 预算 |
| 在线评测闭环 | 中 | 中 | 有真实用户后做 |
| 多租户 + 鉴权 | 高 | 高 | 对外部署前必须做 |
| 流式回答 | 中 | 低–中 | 纯体验优化，可在 M7 后单独排期 |
