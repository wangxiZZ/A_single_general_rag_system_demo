# 技术选型文档

> 对应仓库：`rag_system_demo_test`（包名 `rag_kb`）
> 本文记录**已做出的选型决策**与**被否方案**，格式参照 ADR（Architecture Decision Record）。
> 版本号取自 `uv.lock` 与 `docker-compose.yml` 的实际锁定值，不是"计划使用"。

## 0. 选型前提

题目给出三条硬约束，它们直接砍掉了大量选项：

| 约束 | 影响 |
|---|---|
| 不使用 LangChain / LangGraph 等 RAG 编排框架 | 不能靠 `ConversationalRetrievalChain` 走捷径，检索链路必须自己组织 |
| 不得直接部署或包装现成 RAG 产品（RAGFlow / WeKnora） | 只能借鉴设计，不能把整个产品当黑盒放进来 |
| 允许 LLM / Embedding / 多模态走 API | 因此不必在容器里背模型权重，镜像可以保持小 |

叠加两条工程前提：

- 单机 Docker Compose 交付，验收人 `cp .env.example .env` 后要能一键起
- 运行环境为 8–16 GB 内存的个人机器，空闲态总占用需控制在 3–4 GB

---

## 1. 选型原则

1. **每个组件都必须能被"效果验证"用到**。三路召回是题目硬要求，因此向量库、词法索引、图数据库各自独立可查、可单独评测；不选"一个库糊住三件事"的方案，否则分不清是哪一路在起作用。
2. **宁少一容器，不多少一能力**。每多一个容器就多一份启动失败概率，但为省容器而牺牲题目考点（如图谱召回）是本末倒置。
3. **能在应用层说清的逻辑，不交给框架**。分块、融合、引用校验全部手写，保证可解释。
4. **外部依赖只通过端口访问**。所有选型都可替换：换向量库只改 `infra/milvus/` 一个目录。
5. **默认保守，能力可选**。重排默认关闭、VLM 可关闭、模型未配置也能启动——降级路径必须先于功能存在。

## 3. 重点决策展开

### ADR-004 向量库：Milvus 还是 pgvector

| 维度 | Milvus 2.5 standalone | pgvector | Chroma / LanceDB |
|---|---|---|---|
| 库级隔离 | `partition_key=kb_id` 按库路由；查询仍须带 `kb_id` 等值过滤 | `where kb_id=` 应用层过滤 | 每库一 collection |
| 索引可选性 | HNSW / IVF_FLAT / 量化，参数显式可谈 | 仅 HNSW / IVFFlat | 无 |
| 组件数 | 3（milvus + etcd + minio） | 0（复用 PG） | 0–1 |
| 空闲内存 | ≈1.8 GB | ≈0 | ≈100 MB |
| 验收辨识度 | 高（"向量库"环节可独立演示） | 中（易被视为 PG 附属） | 低 |

**决策**：Milvus 2.5.4 standalone。理由：题目考察 RAG 工程设计，`partition_key` 这种"用引擎能力解决隔离问题"的选择本身就是可解释的设计点；同时与本人既有 Milvus 实践经验一致，降低踩坑成本。

**`partition_key` 不是隔离边界**：它是**路由能力**——按 `kb_id` 把实体散到固定分区，查询带 `kb_id` 等值过滤时只扫对应分区；但**不带过滤的查询仍会扫描全部分区**，跨库结果依然可能返回。因此隔离由两层共同保证：

1. `VectorStore` 端口实现强制注入 `kb_id` 过滤，调用方无法绕过；
2. 隔离测试覆盖"A 库文档在 B 库三通道 0 命中"。

**代价与缓解**：多两个容器、首次启动约 90 s。缓解方式——compose 用 `service_healthy` 串依赖，healthcheck `start_period=90s`；`VectorStore` 端口已抽象，若目标机器内存不足，可切 `PGVectorStore` 实现而不动上层（降级路径见 `docs/design.md` 相关章节）。

**复审触发**：目标机器可用内存 < 6 GB，或需要部署到只有托管 Postgres 的环境。

### ADR-005 词法召回：为什么不是 Elasticsearch

关键字召回最容易的错法是"接个 ES 就完事"。否决理由：

- ES 容器约 1 GB 内存，只是为一个 BM25 通道，性价比低；
- 单机 DEMO 用不满 ES 的高亮、聚合、同义词能力；
- 多一个需要调优的 JVM 服务，启动失败面变大。

**决策**：PG 承担词法召回，关键在于中文分词的正确做法——

1. **入库前**用 jieba 切词并清洗，把结果空格连接后写入 `chunk_lex.lex_tokens`；
2. 建 GIN 索引：`to_tsvector('simple', lex_tokens)`；
3. **查询侧**同样先 jieba 切词，再拼 `to_tsquery('simple', 'a | b | c')`，用 `ts_rank_cd` 排序。

用 `simple` 而非 `english` 配置是刻意的：`english` 会做词干化与停用词处理，对中文有害无益；`simple` 只做小写归一，正好配合"分词已在应用层做完"这一前提。**不要指望 PG 内置中文分词**——那需要 zhparser + SCWS 编译，会给验收人增加编译负担。

**已知短板**：无 BM25 的字段加权与同义词扩展；`ts_rank_cd` 的排序与 Lucene BM25 不完全等价。作为三路之一足够，且这个差距本身是 benchmark 要量化的对象。

### ADR-006 图谱：Neo4j 还是 PG 递归 CTE

题目要求图谱召回完成"抽取 → 持久化 → 利用关系检索 → 返回原文证据"的闭环。

| 维度 | Neo4j 5.25 Community | PG 递归 CTE |
|---|---|---|
| 2 跳查询表达 | `MATCH (e)-[:REL*1..2]-(n)` 一行 | 两层 `with recursive`，边表自连接，可读性差 |
| 实体唯一约束 | `CREATE CONSTRAINT` 原生 | 需自建唯一索引 + 冲突处理 |
| 路径权重聚合 | `relationships(p)` 直接取 | 需在 CTE 里手工累加 |
| 组件成本 | 1 容器 ≈800 MB | 0 |
| 可视化 | Browser 自带，演示友好 | 无 |

**决策**：Neo4j 5.25 Community。图本身不是检索目标，而是"找到 `chunk_id` 的手段"，因此每个关系边**必须带 `chunk_id` 出处**；命中实体后展开 1–2 跳，取边上的 `chunk_id` 集合回 PG 取原文——返回给用户的是原文块，不是三元组。这是题目"仅展示关系图不算完成"的分界线。

### ADR-009 模型接入：为什么统一到 OpenAI 兼容协议

需要三类模型能力：生成、embedding、多模态。若各写一套 SDK，就是三份重试/超时/限流代码。

**决策**：一个 `infra/llm/openai_compat.py`，通过 `LLM_BASE_URL` / `EMBED_BASE_URL` / `VLM_BASE_URL` 分别指向不同厂商的兼容端点：

| 能力 | 默认端点 | 模型 |
|---|---|---|
| 生成与图谱抽取 | `https://api.deepseek.com/v1` | `deepseek-chat` |
| 向量化 | `https://api.siliconflow.cn/v1` | `BAAI/bge-m3`（1024 维） |
| 图片描述 | `https://dashscope.aliyuncs.com/compatible-mode/v1` | `qwen-vl-max` |

**代价**：三家兼容层质量不一，个别参数（如 `response_format` 的严格 JSON 模式）支持程度不同。缓解：图谱抽取不依赖严格 JSON 模式，而是用"提示词约定 + 输出后解析 + span 校验"三重兜底，解析失败即丢弃该批而非重试到超时。

**不选本地 bge-m3 的原因**：镜像 +2.2 GB、首次冷启动要下模型权重，与"一键启动"目标冲突。端口已抽象，若要省 API 花费，可实现 `LocalSentenceTransformerEmbedder` 替换，上层无感。

### ADR-013 分块：父子双层

单个 chunk 越短，向量越"纯"、检索越准；但给 LLM 的上下文越碎、越容易断章取义。
只取其中一种都不对。

**决策**：双层结构。子块 320 tokens（重叠 15%）入索引、参与召回；父块为该二级标题下的整节（≤1200 tokens），命中子块后回填父块作为回答上下文。标题路径（`产品手册 > 3 部署 > 3.2 依赖`）写入子块前缀，缓解"块脱离上下文后语义破碎"。

**代价**：索引条目与存储约 +10%，检索到回填多一次 PG 查询。换来的是"检索精度"与"答案完整度"不必互相妥协。

### ADR-014 融合与重排：RRF 为什么是默认

三路召回的分数天然不可比：向量是余弦相似度（0–1），词法是 `ts_rank_cd`（无量纲、随文档集变化），图谱是"命中种子数 × 路径权重"（自定标度）。任何加权求和都要先解决归一化，而归一化参数会随语料漂移。

**决策**：默认 RRF（Reciprocal Rank Fusion，k=60），只用排名不用分数：

```
score(d) = Σ_over_channels  1 / (k + rank_channel(d))
```

优点：无需调权重、对分数量纲免疫、单通道缺失时自然降权。加权融合保留为 `mode=hybrid_weighted` 备选，权重进 `.env`。

**重排单独决策**（题目要求"自行决定并解释"）：**实现但默认关闭**。理由是——RRF 已解决"分数不可比"，重排要证明的是"在已融合的 top-k 里还能再排出更好的顺序"。这需要数据支撑，而非直觉：引入 cross-encoder 会增加 100–300 ms 延迟与调用成本，对短查询收益小、对长查询与多候选收益明显。因此把 `RERANK_ENABLED=false` 作为默认，等 M7 的 benchmark 用 `RRF vs RRF+rerank` 的 nDCG@10 差值说话，并把结论写进 `docs/benchmark.md`。**这是一个用测量代替猜测的设计，而不是"没做完"。**

重排的两种实现与边界：

| 方式 | 触发 | 说明 |
|---|---|---|
| cross-encoder（默认） | `RERANK_ENABLED=true` 且未指定方式 | 走 `bge-reranker-v2-m3` 兼容 API，对融合后 top-30 重排 |
| LLM listwise（显式） | `rerank=llm`（请求级显式选择） | 不进入检索默认路径；题目未要求，**仅作为对照实验**保留 |

配置键必须三处同步（`config.py` / `.env.example` / `docker-compose.yml`）：
`RERANK_BASE_URL`、`RERANK_MODEL`、`RERANK_API_KEY`、`RERANK_TIMEOUT_S`。
`RERANK_ENABLED` 只控制开关，不承担端点配置。

与 `AGENTS.md` §6.8"查询期不得隐式触发 LLM"的关系：默认检索路径（vector / keyword /
graph / RRF）零 LLM 调用；cross-encoder 是独立的小模型 API，不算生成式 LLM；
`rerank=llm` 必须由调用方显式传参，属于"用户要求重排"而非"系统偷偷调模型"。

### ADR-017 文档状态与"可检索"语义

题目把"上传 → 解析与索引 → 检索"当成一条流程，但工程上这两段必须可分开交付：
M2 交付解析与分块，M3 交付向量/词法/图谱索引。若 M2 结束就把文档标成 `ready`，
MCP 的 `ready_count`、Web 的状态显示、M6 的全链路测试都会把"只有 chunk 行"
误认为"可以检索"——这是本设计里最容易产生假通过的地方。

**状态机**：

| 状态 | 含义 | 进入条件 | 可检索 |
|---|---|---|---|
| `pending` | 已创建，等待 worker | 上传成功 / 重试 | 否 |
| `parsing` | 解析与分块中 | worker 领取任务 | 否 |
| `chunked` | 解析分块完成，索引未做 | chunk 行落库、写入 `chunker_version` | 否（仅 `/chunks` 可查看） |
| `indexing` | 三路索引中 | 向量/词法/图谱任务开始 | 否 |
| `ready` | 三路索引完成 | vector + lexical + graph 全部成功 | 是 |
| `failed` | 任一步失败 | 解析/embedding/图抽取异常，或删除 tombstone | 否 |

转移规则：`pending → parsing → chunked → indexing → ready`；任一步可跳 `failed`；
`failed → pending` 仅通过显式重试（`attempts+1`，先清理残留）。禁止 `chunked → ready`
或 `ready → chunked` 的隐式跳变。

**为什么 `chunked` 必须独立存在**：

1. M2 的验收对象是分块质量，不是检索质量，状态应该如实反映这一点；
2. M3 可以对 M2 的存量数据执行 `reindex`（从 `chunk` 表重建索引，不重新解析）；
3. 换 embedding 模型或换分块参数时，靠 `chunker_version` / `embed_model` 判断是否需要重建。

**降级语义**：`VLM_ENABLED=false` 或单张图片描述失败不阻塞 `ready`——图片块以占位描述
入索引，并把降级记入 `ingest_job.timings`；但向量/词法/图谱三路任一失败必须进 `failed`，
因为题目要求三种召回均可实际调用。

**代价**：状态多一个、迁移多一次；换来 M2/M3 可独立验收，且不会出现"显示 ready 但
三通道检索为空"的故障。

### ADR-018 检索单元与 chunk 数据模型

**问题**：父子双层分块同时服务两个目标——子块要小以便向量纯度高，父块要整以便回答完整。
若不显式约定"哪个块进索引、命中后返回什么"，会出现三类错误：

1. 父块也进向量索引，召回粒度混乱、同一内容重复命中；
2. 图谱边指向父块、检索返回子块，`chunk_id` 对不上，证据无法回溯；
3. 评测金标绑定 chunk id，换 chunk 参数后全部失效。

**决策**：

1. **检索单元 = 子块（`level=child`）**。只有子块写入 Milvus 与 `chunk_lex`；
   父块（`level=parent`）只存 PG 与必要时的 Neo4j 证据节点，用于回答阶段回填。
2. `/search` 的 `SearchHit.chunk_id` 默认是子块 id；**只有图谱证据无法映射到任何子块时**
   才退回父块，并以 `SearchHit.level=parent` 明确标记。回答阶段回填父块时，仍保留
   "由哪个子块命中"的回溯字段。
3. **图谱边的证据映射**：抽取时记录 `evidence_span` 的字符区间，与子块的
   `char_start/char_end` 求交集，取覆盖字符最多的子块；跨子块时取覆盖最大者；
   无交集才退回父块。关系边必须带 `chunk_id` 与 `evidence_span`，否则无法证明证据出处。
4. **确定性 `chunk_id`**：
   `sha256(f"{doc_sha256}:{seq}:{chunker_version}")[:32]`。同一文档、同一序号、同一
   分块版本永远得到同一 id；换分块规则必须递增 `chunker_version`，旧 id 自然失效。
5. 父/子关系用 `parent_id` 表达：父块 `level=parent` 且 `parent_id IS NULL`，子块
   `parent_id` 指向父块；`unique(doc_id, seq)` 保证重跑幂等。

**PG `chunk` 字段表**：

| 字段 | 类型 | 空 | 说明 |
|---|---|---|---|
| `id` | varchar(32) | 否 | 确定性 chunk id，见决策 4 |
| `kb_id` / `doc_id` | uuid | 否 | 所有检索必须带 `kb_id` |
| `parent_id` | varchar(32) | 是 | 子块指向父块；父块为 NULL |
| `level` | enum | 否 | `parent` / `child` |
| `kind` | enum | 否 | `text` / `image` / `table` |
| `content` | text | 否 | 图片块为 VLM 描述 + 前后文 |
| `heading_path` | text[] | 是 | 如 `["产品手册","3 部署","3.2 依赖"]` |
| `page_no` / `page_to` | int | 是 | PDF 必填；docx 为 NULL |
| `bbox` | jsonb | 是 | PDF 必填；docx 为 NULL |
| `char_start` / `char_end` | int | 否 | 相对文档正文串联文本的偏移 |
| `seq` | int | 否 | 阅读顺序，`unique(doc_id, seq)` |
| `token_count` | int | 否 | 估算 token 数（`chars_per_token`） |
| `image_id` | uuid | 是 | 图片块指向 `doc_image.id` |
| `meta` | jsonb | 是 | 低权重/降级标记（如 VLM 占位），不参与检索过滤 |
| `chunker_version` | text | 否 | 分块规则版本；变更即需重建 |

`chunk_lex` 只存子块：`chunk_id` 外键、`lex_tokens`（jieba 结果空格连接），
`tsv` 为 `GENERATED ALWAYS AS (to_tsvector('simple', lex_tokens)) STORED`。
Milvus `chunk_vec` 同样只写子块，字段为 `id / kb_id / doc_id / level / vector`。

**格式能力差异**（不强行统一，避免为了 docx 造页码）：

| 字段 | PDF | docx |
|---|---|---|
| `page_no` / `page_to` | 必填 | NULL |
| `bbox` | 必填 | NULL |
| `char_start` / `char_end` | 必填 | 必填（正文串联文本） |
| `seq` | 必填 | 必填（XML body 顺序） |
| 图片定位 | `page_no + bbox` | `seq + 前后段落` |

**代价**：

- 引用展示对 docx 只能给"第 N 段 / 标题路径"，不能给页码，列为已知限制；
- 子块索引 + 父块存储使 PG 行数约 +10%，回答阶段多一次父块查询；
- `chunker_version` 变更需要整库重建，因此 M7 评测前必须冻结分块规则。

**被否方案**：

| 方案 | 否决原因 |
|---|---|
| 只存子块、不回填父块 | 回答上下文断裂，长文档容易断章取义 |
| 父子块都进向量/词法索引 | 召回重复、融合后排位失真、评测口径混乱 |
| 用 `inline_shapes` 顺序给 docx 定位 | 顺序不可靠（见 ADR-008），图片会错位 |
| 用自增主键做 chunk_id | 重新入库后 id 漂移，评测金标与 upsert 幂等全部失效 |

### ADR-019 端口契约与异步策略

**问题**：`application/` 要同时被 REST 路由、摄取 worker、CLI 与测试复用。如果它直接
`import` 某个存储客户端，分层就破了；如果端口方法既有同步又有异步，调用方就得为每个
端口写两套包装，最终一定会在协程里误调同步 SDK，把事件循环阻塞住。

**决策**：端口是能力名，不是表名或 SDK 名。完整清单：

| 端口 | 职责 | 调用形态 |
|---|---|---|
| `MetadataRepository` | KB / Document / Chunk / IngestJob / QueryLog 的读写；任务领取用 `claim_job`（`FOR UPDATE SKIP LOCKED`） | `async` |
| `VectorStore` | 建集合、维度校验、upsert、`search(kb_id=...)`、`delete_by_doc`、计数 | `async` |
| `LexicalIndex` | 子块入库、`search(kb_id=...)`、`delete_by_doc`、计数 | `async` |
| `GraphStore` | schema 初始化、实体/关系写入、候选实体查询、多跳展开、`delete_by_doc`、计数 | `async` |
| `Embedder` | `embed_documents` / `embed_query`，内部按 `EMBED_BATCH_SIZE` 分批 | `async` |
| `LLM` | `chat` / `structured_json`，用于图谱抽取与回答 | `async` |
| `VLM` | `describe_image`，单图描述 | `async` |
| `Reranker` | `rerank(query, candidates)`；cross-encoder 与 listwise 两种实现 | `async` |
| `Parser` | `parse(data, filename) -> list[Block]`；纯 CPU，**同步** | `sync` |
| `Storage` | 上传件与图片的落盘/读取/删除 | `async` |

**异步约定**：

1. 所有 I/O 端口方法声明为 `async def`；
2. 同步 SDK（psycopg 同步连接、pymilvus、neo4j 同步 driver、本地文件写入）由适配器内部
   用 `anyio.to_thread.run_sync` 包装，**禁止在协程里直接调用阻塞函数**；
3. `Parser.parse()` 是 CPU 密集型同步方法，由 worker 用
   `await anyio.to_thread.run_sync(parser.parse, ...)` 调用；
4. LLM / Embedding / VLM 的并发由 `LLM_MAX_CONCURRENCY`、`EMBED_MAX_CONCURRENCY`、
   `VLM_MAX_CONCURRENCY` 控制，在适配器内部用 `asyncio.Semaphore`，不把限流责任丢给调用方；
5. 端口方法只抛 `domain/errors.py` 的领域异常；第三方异常由 infra 转换，application
   决定重试或标记失败，api 映射 HTTP 状态码。

**注入方式**：`main.py` 的 lifespan 构造所有适配器，存到 `app.state`，再把它们注入
application 服务；worker 与 CLI 复用同一组应用服务，不各自 new 一套仓储。测试用 fake
端口构造服务，不需要容器。

**代价**：每个同步客户端都多一层 `to_thread` 包装，调用栈略深；批量写入需要确认包装粒度
（整批一次 `to_thread`，不要逐条）。

**被否方案**：

| 方案 | 否决原因 |
|---|---|
| 端口全部同步 + FastAPI 路由用 `def` 走线程池 | API 能跑，但 worker 的取消/重试与事件循环语义分叉，且无法统一限流 |
| application 直接 import `infra.postgres.repository` | 破坏分层；测试必须起容器；换存储要改业务层 |
| 在路由里直接调 infra | 同上的更差版本，检索与索引逻辑会散进 `api/` |

### ADR-020 实体与关系的单一存储

**问题**：原型设计里 PG 有 `entity` / `chunk_entity` 两张表，Neo4j 又存一份
`(:Entity)`。两份数据要双写、双删、双重建：任何一次图抽取重跑或文档删除，只要一处漏同步，
就会出现"PG 说实体在、Neo4j 查不到边"或反过来的情况。删除验收要求"三通道 0 命中"，
双份真相对这个断言是直接的威胁。

**决策**：**Neo4j 是实体与关系的唯一存储**；PostgreSQL 删除 `entity`、`chunk_entity`
两张表，只保留 chunk 文本与元数据。

**图模型**：

| 元素 | 定义 | 关键属性 |
|---|---|---|
| `(:Doc)` | 文档节点 | `kb_id, doc_id` |
| `(:Chunk)` | 证据块节点（子块优先，父块仅作回退） | `kb_id, chunk_id, level` |
| `(:Entity)` | 归一化实体 | `kb_id, name, normalized, type` |
| `[:MENTIONS]` | Chunk → Entity | `span`（在 chunk 内的字符区间） |
| `[:REL]` | Entity → Entity | `type, weight, chunk_id, evidence_span` |

唯一约束：`Entity(kb_id, normalized, type)`。关系边必须同时带 `chunk_id` 与
`evidence_span`，否则无法回溯原文，直接不允许入库。

**实体归一**：全角转半角、统一小写、去掉成对括号内的补充说明；归一后的值写入
`normalized`，原名保留在 `name` 供展示。归一冲突时保留出现频次最高者，频次相同保留
首次出现者。

**查询期种子链接**：由 `GraphStore.candidate_entities(kb_id, terms)` 提供候选，
应用层按"精确 → 别名 → 2-gram 模糊"三档选择并打分；无匹配返回空列表，不抛异常。
链接与打分是业务逻辑，放 `application/search_service.py`，不放 `infra/neo4j/`。

**删除级联**（与 ADR-020 同一条验收口径）：

1. PG：删除 `document` 行 → `chunk` / `doc_image` / `ingest_job` / `query_log` 级联；
2. Milvus：`delete_by_doc`，按 `doc_id` 过滤原子删除；
3. Neo4j：删除该文档的 `:Chunk` 与 `:Doc`，再清理因此变成孤儿的 `:Entity`；
4. 磁盘：删除上传件与 `data/images/<doc_id>/`；
5. 断言：三通道计数为 0、磁盘目录不存在，而不是只看接口 200。

**重建路径**：图谱可以从 `chunk` 表 + 原文重新抽取，不依赖 PG 实体表；`reindex` 命令
覆盖向量、词法、图谱三路，删除与重建走同一条路径。

**可用性语义**：Neo4j 不可用时，`mode=graph` 返回 503；`mode=hybrid` 降级为其余两路，
并在 `channels[]` 中标记 graph 为 `error`，不把整体请求打成失败。

**代价**：查询期多依赖一个存储；Neo4j 成为图谱通道的单点。换来的是删除/重建路径唯一、
不会出现双写漂移，且 `chunk_entity` 这类只为"回溯"存在的表不再需要维护。

**被否方案**：

| 方案 | 否决原因 |
|---|---|
| PG + Neo4j 双写实体 | 两份真相，删除级联与重建都容易漏；验收断言不可靠 |
| 实体只在 PG，Neo4j 只存边 | 边仍要引用实体，跨库 join 更复杂；且 `chunk_entity` 与边重复 |
| 只保留 PG 递归 CTE 图 | 见 ADR-006：多跳表达与路径聚合复杂度高 |

### ADR-021 配置与环境变量契约

**问题**：`Settings` 字段多，但容器内的 app 只拿到 compose `environment` 白名单里的值。
`.env` 只被 compose 用于 `${VAR}` 插值，**应用本身不会读它**（镜像里也没有 `.env`）。
因此某个字段没写进 compose 时，用户在 `.env` 里改了也不生效，而且没有任何报错——
"配置静默失效"比启动失败更难排查。

**决策**：

1. **compose 的 `environment` 是容器内唯一透传通道**；`.env` 只承担 compose 插值。
2. `Settings` 的每个字段必须在 `services.app.environment` 中出现；不允许"有字段但没透传"。
3. 新增 `tests/unit/test_config_compose_sync.py`：解析 `Settings.model_fields` 与
   `docker-compose.yml`，缺失即失败。YAML 解析用 dev 依赖 `pyyaml`，不引入 runtime 依赖。
4. 密钥只从环境变量读，不进镜像、不写进 `docker-compose.yml` 字面量。

**当前缺口与处理**：

| 字段 | 现状 | 处理 |
|---|---|---|
| `APP_NAME` | 未透传 | compose 补 `APP_NAME: ${APP_NAME:-rag-kb}` |
| `PG_POOL_MIN` / `PG_POOL_MAX` | 未透传 | compose 补，默认 `1` / `8` |
| `MILVUS_TOKEN` | 未透传 | compose 补，默认空 |
| `NEO4J_DATABASE` | 未透传 | compose 补，默认 `neo4j` |
| `EMBED_TIMEOUT_S` / `VLM_TIMEOUT_S` | 未透传 | compose 补，默认 `60` / `90` |
| `CHARS_PER_TOKEN` | `.env.example` 有，compose 未透传 | compose 补，默认 `1.5` |
| `ALLOWED_MIME` | 未透传，且 tuple 走环境变量有解析歧义 | **移出 `Settings`**，改为 `config.SUPPORTED_MIME` 常量，由上传校验使用 |
| `RERANK_BASE_URL` / `RERANK_MODEL` / `RERANK_API_KEY` / `RERANK_TIMEOUT_S` | 尚未定义 | 新增字段与 compose 项 |
| `QA_MAX_CONTEXT_TOKENS` | 尚未定义 | 新增，默认 `6000` |
| `GRAPH_NEIGHBOR_LIMIT` | 尚未定义 | 新增，默认 `50` |
| `HYBRID_WEIGHT_VECTOR` / `HYBRID_WEIGHT_KEYWORD` / `HYBRID_WEIGHT_GRAPH` | 尚未定义 | 新增，默认 `1.0` / `1.0` / `1.0`，仅 `mode=hybrid_weighted` 使用 |
| `EMBED_MAX_CONCURRENCY` | 尚未定义 | 新增，默认 `4` |
| `VLM_MAX_CONCURRENCY` | 尚未定义 | 新增，默认 `2` |

**新增配置的固定动作**（与 `AGENTS.md` §3.6 对应）：

1. `config.py` 加字段与默认值；
2. `.env.example` 加同名变量与注释；
3. `docker-compose.yml` 的 app `environment` 加透传；
4. 更新本文 ADR 与 `docs/architecture.md` 的配置表；
5. 跑 `test_config_compose_sync.py`。

**代价**：compose 的环境变量清单会变长；但换来的是一条机器可验证的契约，避免"文档说
支持、容器里其实没生效"。

**被否方案**：

| 方案 | 否决原因 |
|---|---|
| app 服务直接 `env_file: .env` | `.env` 同时承担宿主机直跑与容器部署，`postgres` / `localhost` 地址会互相污染；还容易把密钥带进镜像上下文 |
| 应用自行读取 `.env` | 镜像必须包含 `.env`（泄密风险），且与 compose 注入的优先级不清 |
| 只靠人工核对三处同步 | 已经出现过漏传（本 ADR 的缺口表就是证据），不可靠 |

### ADR-022 失败口径与评测金标

**失败口径**：边界测试最容易"假通过"的地方是把所有失败都断言成 `status=failed`。
上传阶段的拒绝、解析阶段的失败、索引阶段的失败，副作用和可重试性完全不同，必须分开。

| 场景 | 接口 / 状态 | 副作用 | 重试 |
|---|---|---|---|
| 超过 `MAX_UPLOAD_MB` | **413** | 不建 document 行、不落盘、不产生任务 | 不需要（用户换文件） |
| MIME / 扩展名 / magic bytes 不符 | **415** | 同上 | 不需要 |
| 同库内 `sha256` 重复 | **409**（返回已有 document id） | 不重复落盘、不重复建任务 | 不需要 |
| 损坏 PDF/docx、解析异常 | `status=failed` | 清理已写 chunk；无向量/图/词法残留 | 可重试 |
| PDF 无可提取文本（扫描件） | `status=failed`，错误含"不支持 OCR" | 无 chunk | 可重试（换文件） |
| `EMBED_API_KEY` 未配置 / embedding 调用失败 | `status=failed`，在**写索引前**失败 | 无向量/词法写入 | 配置后重试 |
| 图抽取整体不可用（LLM 连续失败） | `status=failed` | 清理已写节点/边 | 可重试 |
| span 校验丢弃个别实体/关系 | 不算失败 | 记入 `ingest_job.timings` 的丢弃计数 | 不重试 |
| 摄取中删除文档 | 文档行已删；**tombstone** 中止任务 | 清理该 doc 已写数据 | 不重试 |

**约束**：

- `error` 字段必须是可操作的人类可读信息（阶段 + 原因 + 文件名），不含堆栈与密钥；
- 失败路径先清理再置 `failed`；清理本身失败也要记录，删除/重试会再次清理；
- "无脏索引"的断言口径：`chunk` 行数、Milvus 实体数、Neo4j 节点/边数均为 0；
- 重试入口：`POST /documents/{id}/retry`，`attempts+1`，状态回 `pending`。

**评测金标**：

```json
{
  "id": "q-001",
  "question": "3.2 节的依赖安装要求是什么？",
  "type": "single_hop | multi_hop | term | image | unanswerable",
  "gold": [{"doc_id": "...", "page_no": 12, "char_start": 430, "char_end": 610}],
  "reference_answer": "..."
}
```

- 金标用**页码 + 字符区间**（或页面级命中），**不用 chunk_id**：换分块参数、换 chunker
  版本后金标仍然有效；
- 命中判定：证据区间与金标区间的交集 / 并集 ≥ 阈值，或页码相同；阈值写进
  `scripts/bench/metrics.py` 并在报告中说明；
- 样本 **20–30 条**，覆盖单跳、多跳、术语、图片、不可回答五类；不可回答题用于衡量
  拒答准确率；
- 维度只保留 `mode（vector/keyword/graph/hybrid）× rerank（on/off）`；
- **M7 开始前冻结 chunking 规则与 chunk_id 生成规则**，避免评测期间索引漂移。

**被否方案**：

| 方案 | 否决原因 |
|---|---|
| 金标直接绑定 chunk id | 换分块参数或 chunker 版本即全部失效，评测结果不可比 |
| 数十条样本全手工标注 | 单机 DEMO 的时间成本过高，且标注质量难保证；20–30 条并抽检足够比较通道差异 |
| 按多个 chunk 尺寸重复跑分 | 每个尺寸都要重建索引并重新标注，M7 的时间预算装不下 |
| 只用 LLM-as-judge、不留参考区间 | 无法计算 Recall/MRR/nDCG，也无法定位是哪一路召回失败 |

| app | 本地构建（`python:3.12-slim` + uv） | 非 root 运行 |

### 4.3 兼容性矩阵（连通性已实测）

| 组合 | 结论 | 验证方式 |
|---|---|---|
| pymilvus 2.6.18 ↔ Milvus 2.5.4 | ✅ 连通性已验；**写入/检索/删除冒烟待 M3-01** | `/readyz` 中 `list_collections()` 成功；M3-01 补 `insert → search → delete` |
| neo4j 驱动 6.4.1 ↔ server 5.25 | ✅ 连通性已验 | `/readyz` 中 `RETURN 1` 成功 |
| psycopg 3.3.9 ↔ PG 16.16 | ✅ 连通性已验 | `/readyz` 中 `server_version` 查询成功 |
| Milvus 2.5.4 ↔ etcd 3.5.5 | ✅ 连通性已验 | 容器 healthy，collection 数可读 |

> 连通性成功不等于 API 兼容：Milvus 的写入、索引构建与聚合查询走的是另一组 gRPC 接口。
> 因此把 pymilvus 的兼容性列为待验证项（TD-08），在 M3-01 用真实写读删闭环确认；
> 若客户端与服务端不配套，优先把服务端升到 2.6.x，而不是在没有证据的情况下换客户端。

> 关于 Milvus 版本：本机已存在 `milvusdb/milvus:v3.0.2` 镜像，但仍选择 v2.5.4——`uv.lock`
> 锁定的客户端是 pymilvus 2.6.18，目前只验证了连通性；写入/检索/删除的 API 兼容性
> 列为 TD-08，由 M3-01 冒烟确认。v3.0.x 的客户端/服务端配对完全未验证，不为省一次
> 2 GB 拉取引入不确定性。

## 5. 被否方案汇总

| 方案 | 否决原因 | 保留价值 |
|---|---|---|
| LangChain / LangGraph / LlamaIndex | 题目硬约束 | — |
| 直接部署 RAGFlow / WeKnora | 题目明确禁止"包装现成产品" | 借鉴其分块与引用展示的交互设计 |
| pgvector 替代 Milvus | 隔离能力弱、验收辨识度低 | 作为内存不足时的降级实现 |
| Elasticsearch / OpenSearch | 为单通道 BM25 引入 1 GB 容器 | 若将来需要高亮与同义词，可替换 `LexicalIndex` |
| Chroma / LanceDB | 共享卷并发写风险；每库一 collection 难演示隔离 | — |
| graph 用 PG 递归 CTE | 多跳 SQL 复杂度高、无可视化 | 无 Neo4j 环境时的备选 |
| 实体同时存 PostgreSQL 与 Neo4j（双写） | 两份真相，删除级联、重建与验收断言都容易漂移 | 作为 ADR-020 的历史方案保留，不再采用 |
| 端口全部同步 + FastAPI 路由用 `def` 走线程池 | API 可跑，但 worker 的取消/重试与限流语义分叉 | 仅在小工具里可接受，主服务不采用（ADR-019） |
| 评测金标绑定 `chunk_id` | 换分块参数或 chunker 版本即失效，无法横向比较 | 仅在单次实验内部可用；正式金标用页码/字符区间（ADR-022） |
| `ALLOWED_MIME` 暴露为环境变量 | tuple 的逗号/JSON 解析有歧义，且它由 parser 能力决定，不是部署参数 | 改为 `config.SUPPORTED_MIME` 常量（ADR-021） |
| Celery + Redis | 单机 DEMO 运维面大于收益 | worker 抽成独立进程即可扩展 |
| React + Vite 前端 | 需 Node 构建阶段，交付风险高 | 若后续要做检索调试面板可迁移 |
| 本地 bge-m3（sentence-transformers） | 镜像 +2.2 GB，冷启动下载权重 | 可用 `Embedder` 端口替换以省 API 花费 |
| 严格 JSON 模式做图谱抽取 | 各厂商支持不一，失败即阻塞 | 改为"解析 + span 校验"兜底 |
| 流式输出（SSE） | 题目未要求，且会让引用回校验复杂化 | 明确记录为已知限制，而非遗漏 |

## 6. 已知技术债与复审计划

| 编号 | 技术债 | 影响 | 复审时机 |
|---|---|---|---|
| TD-01 | 词法召回用 `ts_rank_cd` 而非真 BM25 | 排序与主流实现有差异 | M7 benchmark 量化差距 |
